Keycloak AD Integration — Local Active Directory Account Import

This document is a supplement to windows-deploy-guide.html. It covers connecting a local Active Directory domain controller to Keycloak so employees can log in to all AI platform apps with their domain accounts. It applies to the Hyper-V local DC test environment.

1. Prerequisites

  • The Keycloak container can reach the AD domain controller's LDAP port (default 389, or 636 for LDAPS)
  • An AD service account exists (format: CN=svc_keycloak,OU=ServiceAccounts,DC=company,DC=com)
  • Keycloak deployment and realm creation are already completed per the main document

2. Building the Hyper-V Local DC Test Environment

2.1 Scenario

Network isolation: Docker Desktop (WSL2) and the Hyper-V Default Switch are on different virtual networks, so containers cannot reach the DC VM directly. Traffic must be forwarded through the Windows host. The following applies to Windows 11 + Docker Desktop + Hyper-V local testing.

2.2 Enable Hyper-V and Create the DC VM

# Admin PowerShell — enable Hyper-V (requires reboot)
Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All

# Download the Windows Server evaluation ISO (180-day free trial)
# https://www.microsoft.com/en-us/evalcenter/evaluate-windows-server
  1. Hyper-V Manager → New Virtual Machine → name it test-dc, Generation 2
  2. Memory: 2048 MB, dynamic memory disabled
  3. Network: temporarily select the Default Switch (finish the OS install first, switch to the Internal Switch later)
  4. Disk: 40 GB, attach the Windows Server ISO

2.3 Install AD DS and Promote to Domain Controller

Use the Default Switch to finish the Windows Server install and AD DS deployment first; the fixed IP is configured in the next section.

# Inside the VM — after install, set a temporary static IP first (Default Switch NAT subnet, check with ipconfig)
netsh interface ip set address "Ethernet" static 172.25.80.100 255.255.240.0 172.25.80.1
netsh interface ip set dns "Ethernet" static 127.0.0.1

# Install the AD DS role and promote to domain controller
Install-WindowsFeature -Name AD-Domain-Services -IncludeManagementTools
Install-ADDSForest -DomainName "testcompany.local"   -SafeModeAdministratorPassword (ConvertTo-SecureString "Passw0rd!" -AsPlainText -Force)   -InstallDNS -Force
# The VM reboots automatically

2.4 Configure Docker ↔ Hyper-V DC Network Connectivity

Under the current network structure, Docker Desktop (WSL2) and the Hyper-V DC sit on two isolated virtual networks. To let the Keycloak container reach the DC, you need a stable forwarding path on the Windows host.

One-click Detect + Fix Script

Recommended unified script:setup-hyperv-dc-network.ps1
  • Usage 1: .\setup-hyperv-dc-network.ps1 — detect + auto-fix + connectivity verification
  • Usage 2: .\setup-hyperv-dc-network.ps1 -Detect — detect only, no changes

The script covers: virtual switch creation / host IP configuration / DC VM NIC attachment / NAT rules / portproxy port forwarding / firewall rules / Layer-3 connectivity verification. Run in Admin PowerShell.

Manual Steps (Reference)

If you prefer not to use the script, run the following command chains manually. The script does exactly the same thing internally.

  1. Create the Internal virtual switch + host IP + NAT 
    # Admin PowerShell
New-VMSwitch -Name "DockerDCBridge" -SwitchType Internal

# Assign a fixed IP to the host-side virtual adapter
$ifAlias = (Get-NetAdapter | Where-Object { $_.Name -like "*DockerDCBridge*" }).InterfaceAlias
New-NetIPAddress -InterfaceAlias $ifAlias -IPAddress 192.168.99.1 -PrefixLength 24

# (optional) Give the DC internet access
New-NetNat -Name "DockerDC-NAT" -InternalIPInterfaceAddressPrefix 192.168.99.0/24
  2. Add a NIC to the DC VM and connect it to the new switch (does not interrupt the DC; keeps the original Default Switch NIC) 
    Add-VMNetworkAdapter -VMName DC -SwitchName "DockerDCBridge"
  3. Set a static IP on the new NIC inside the DC VM

    Enter the DC VM console, open an admin CMD/PowerShell (use ipconfig first to find the newly added NIC name):

    netsh interface ip set address "Ethernet 3" static 192.168.99.10 255.255.255.0 192.168.99.1
netsh interface ip set dns "Ethernet 3" static 127.0.0.1

    If the NIC name is not Ethernet 3, check with Get-NetAdapter first.

Temporary: Default Switch Approach

If you don't want to create an Internal Switch, you can keep the Default Switch, but it is recommended to set the DC IP to a fixed address within that NAT subnet, or set up MAC address reservation in the Hyper-V NAT. Each time the DC IP changes, you must re-run the portproxy commands in the next section.

# Check the DC's current IP (most accurate to run ipconfig inside the VM)
ipconfig

# Or check the ARP table from the host
arp -a | findstr "DC-MAC-address"

Get-ADUser -Filter * | Select-Object Name, SamAccountName, Enabled

3. Docker Container Access to Hyper-V DC (Port Forwarding)

3.1 Why Port Forwarding Is Needed

Network topology:
  • Docker Desktop container network: WSL2 virtual network (isolated from Hyper-V)
  • Hyper-V DC VM: on the Internal Switch private network (recommended: 192.168.99.0/24) or the Default Switch NAT subnet
  • Connectivity approach: use Windows host netsh portproxy to forward host ports to the Hyper-V VM
  • Containers reach the host via host.docker.internal, then port forwarding reaches the DC VM

3.2 Configure Port Forwarding

The following commands assume the Internal Switch from section 2.4 with the DC VM fixed IP 192.168.99.10. If you keep the Default Switch, replace connectaddress with the DC's current dynamic IP.

The script covers this step:setup-hyperv-dc-network.ps1 automatically completes portproxy + firewall configuration; no manual steps needed.

Manual Configuration (Reference)

# Admin PowerShell
# Delete old rules first (to avoid duplicates)
netsh interface portproxy delete v4tov4 listenport=389
netsh interface portproxy delete v4tov4 listenport=636

# Add LDAP/LDAPS port forwarding; listenaddress=0.0.0.0 ensures host.docker.internal can also match
netsh interface portproxy add v4tov4 listenport=389 listenaddress=0.0.0.0 connectport=389 connectaddress=192.168.99.10
netsh interface portproxy add v4tov4 listenport=636 listenaddress=0.0.0.0 connectport=636 connectaddress=192.168.99.10

# Open the firewall
netsh advfirewall firewall add rule name="DC-LDAP" dir=in protocol=tcp localport=389 action=allow
netsh advfirewall firewall add rule name="DC-LDAPS" dir=in protocol=tcp localport=636 action=allow

# Verify forwarding
netsh interface portproxy show all
Test-NetConnection -ComputerName 127.0.0.1 -Port 389
Test-NetConnection -ComputerName 192.168.99.10 -Port 389

3.3 Verify the Docker Container Can Reach the DC

The official Keycloak image is RHEL UBI 9 (not Alpine) and does not include apk. Verify using bash TCP redirection:

# Quick TCP connectivity check
docker exec keycloak bash -c 'exec 3<>/dev/tcp/host.docker.internal/389 && echo "LDAP reachable" && exec 3>&-'

# For a full LDAP query, use ldapsearch (must be installed in the container first)
docker exec keycloak sh -c "microdnf install -y openldap-clients 2>/dev/null; ldapsearch -H ldap://host.docker.internal:389 -D 'CN=svc_keycloak,CN=Users,DC=testcompany,DC=local' -w  -b 'CN=Users,DC=testcompany,DC=local' '(objectClass=user)'"
# Expected: returns zhangsan, lisi, svc_keycloak, etc.

Phase 3 in the script also performs connectivity verification automatically.

  3. Go to the Users page to confirm the domain users have appeared
Common mistakes:
  • Bind DN format: must use the LDAP format CN=account,CN=Users,DC=xxx,DC=local, not the NetBIOS format DOMAIN\account
  • Username LDAP attribute ≠ cn: use sAMAccountName, which is the AD login name. Using cn will prevent users from logging in with their short account name
  • Search scope: if domain users are spread across multiple OUs (e.g. OU=IT,OU=Hangzhou,...), you must select Subtree

4.2 Configure LDAP Group Mapping (Optional)

Map AD groups to Keycloak roles:

  1. Click the LDAP Provider you just created in the User Federation list
  2. Mappers tab → add group-ldap-mapper
  3. Set Groups DN: CN=Users,DC=testcompany,DC=local
  4. After saving, AD groups are automatically mapped to Keycloak

4.3 Verification

  1. Confirm users are imported: Keycloak admin console → Users → you should see the domain users synced from AD. On a second sync, the console shows 0 imported users, N updated users — "0 imported" only means there are no new users, not a failure.

Method A: Test via the Keycloak Account Console (recommended, simplest)

Keycloak's built-in self-service account page requires no downstream app configuration and can directly test whether an AD domain account can log in.

  1. Open a browser (a private/incognito window is recommended to avoid session cache interference)
  2. Go to http://127.0.0.1:9090/realms/enterprise-ai/account
  3. On the login page, enter the AD domain user's credentials:
    • Username: aitest1 (sAMAccountName) or aitest1@chxia.lab (UPN) — both formats work
    • Password: the domain user's password set in AD
  4. Click Sign In
  5. Expected result: the page redirects to the Account Console, with the username in the top-right corner, where you can see profile and security settings
If login fails:
  • Invalid username or password → wrong password or the user is outside the Users DN scope. Confirm the password on the DC and check Keycloak's Users DN
  • Account is disabled → the AD user is disabled on the domain controller (Enabled = False)
  • No response / blank screen → press F12 to open DevTools → check the Console + Network panels for error details

Method B: Verify User Status via the Keycloak Admin Console

  1. Keycloak admin console → Users
  2. Search for the domain username (e.g. aitest1)
  3. Click the user → Attributes tab: you should see attributes like LDAP_ID, LDAP_ENTRY_DN, indicating the user came from LDAP sync rather than being created locally
  4. Sessions tab: if Method A logged in successfully, there is an active session record here

Method C: Test After Connecting a Downstream App (later step)

Once the Keycloak AD login chain works, any app connected to Keycloak OIDC SSO will show the Keycloak login form, where you simply enter the domain account. For example, after Dify is configured with SSO, open http://127.0.0.1/apps in the browser → automatically redirects to the Keycloak login page → enter aitest1 + domain password → log in and enter the Dify workspace.

Passing any of the three verification methods means the AD → Keycloak chain is working. Method A is the most direct and is recommended first.

6. Cleanup (After Testing)

# Stop and delete the DC VM
Stop-VM DC -Force
Remove-VM DC

# Delete port forwarding
netsh interface portproxy delete v4tov4 listenport=389
netsh interface portproxy delete v4tov4 listenport=636

# Delete firewall rules
netsh advfirewall firewall delete rule name="DC-LDAP"
netsh advfirewall firewall delete rule name="DC-LDAPS"

# Delete the NAT and Internal Switch
Remove-NetNat -Name "DockerDC-NAT" -Confirm:$false
Remove-VMSwitch -Name "DockerDCBridge" -Force

# If an old InternalSwitch (Private type, VM-to-VM only) still exists, clean it up too
Remove-VMSwitch -Name "InternalSwitch" -Force
