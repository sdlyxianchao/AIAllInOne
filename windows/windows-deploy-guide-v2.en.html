2. Prerequisites

1Docker Desktop configuration

Docker Desktop uses the WSL2 backend by default after installation (no extra config needed). To manually adjust resource limits, create a .wslconfig file in your user directory:

# %UserProfile%\.wslconfig (e.g. C:\Users\your-username\.wslconfig)
[wsl2]
memory=24GB       # Docker max memory (min 16GB, recommended 24~32GB; allocate about half of host memory)
processors=8      # CPU cores (per host physical cores)
swap=4GB

After saving, run wsl --shutdown in PowerShell, then restart Docker Desktop to apply.

5Pin the host intranet IP (recommended; otherwise the external address changes)

When the host joins the company intranet over WiFi, the router's DHCP dynamically assigns the IP, which can change after reboot or lease expiry. When it changes, all employee access addresses (see 1.4 Intranet Address List) break. It is recommended to reserve a fixed IP via DHCP reservation (MAC binding) on the router:

  1. Find the WiFi adapter MAC: run ipconfig /all in PowerShell, look for the physical address of "Wireless LAN adapter WLAN" (e.g. 60-A3-E3-41-8F-61)
  2. Log into the router admin (e.g. Xiaomi router http://192.168.31.1) → LAN settings / DHCP static IP assignment
  3. Add a rule: MAC 60-A3-E3-41-8F-61 → IP 192.168.31.117, save
  4. Reconnect WiFi or reboot the router, confirm the IP is fixed to 192.168.31.117
DHCP reservation is more robust than setting a static IP in Windows (router-managed, no IP conflicts, transparent to Windows). If you switch to a wired NIC, you can reserve its MAC the same way.

3.5Known issue fix: force Ghost to SQLite

If the ghost container keeps Restarting in the previous step, run docker logs ghost and see Error: connect ECONNREFUSED <server-IP>:3306 — this means the ghost-data volume contains a leftover config.production.json pointing to MySQL (leftover from an old deployment). Ghost reads that stale file instead of defaulting to SQLite. The Windows stack has no MySQL for Ghost, so it can't connect.

Fix: explicitly declare SQLite under the ghost service's environment in docker-compose.yml, overriding the leftover config in the volume with env vars:

# The environment section of the ghost service in docker-compose.yml
  ghost:
    image: ghost:5-alpine
    container_name: ghost
    restart: always
    ports:
      - "8090:2368"
    environment:
      url: http://127.0.0.1:8090
      # Force SQLite, overriding any leftover MySQL config.production.json
      database__client: sqlite3
      database__connection__filename: /var/lib/ghost/content/data/ghost.db
      database__use_null_pool: "true"
    volumes:
      - ghost-data:/var/lib/ghost/content
    networks:
      - ai-platform

Rebuild the container after the change:

docker compose up -d ghost

# Wait 10 seconds, then check logs to confirm SQLite started successfully
docker logs ghost --tail 20
⚠️ Note: Docker Desktop volumes are not visible: Under Windows + Docker Desktop WSL2, /var/lib/docker/volumes/windows_ghost-data/_data/ is not visible in the host git bash (volume data is sealed inside the WSL2 virtual disk), so you can't directly delete the config.production.json inside. You must use the "env-var override" route so Ghost reads env vars first at startup.
📌 Why not just delete the volume? Deleting the volume docker volume rm windows_ghost-data also works, but loses all published posts/themes/uploads. The env-var override keeps the data and only changes the DB connection path. Ghost 5.x's default SQLite is fully sufficient for an enterprise portal; no extra MySQL is needed.
Logs show Ghost database ready in X.Xs + Ghost booted in X.Xs + Database is in a ready state means the fix worked. curl.exe -I http://127.0.0.1:8090 returns HTTP 200.

"Skill Manager" Skill (install first, for employees to find/install/update skills)

A guided skill-market skill is built in; employees install it first, then ask "what skills are there / install X for me / update skills" in a conversation. It doesn't touch DeepChat's internal directories (100% reliable), and only: reads market_url from config.json → requests the /skills list → filters/recommends → gives install instructions → compares version to suggest updates. The Ghost download page has a pinned "install the skill manager first" hint at the top.

# The skill manager's own market address (packaged into the zip for employees)
# mcp-gateway/skills/skill-market/config.json
# ⚠️ Use a hostname, not an IP (DeepChat masks IPs)
# ⚠️ <market-hostname> is a deployment parameter, must be replaced (see "Auto / Manual" below)
{ "market_url": "http://<market-hostname>:3100" }
⚠️ Important: market_url uses a hostname, and <market-hostname> is a deployment parameter that must be replaced. DeepChat's agent environment masks IP addresses into [IP_ADDRESS_REDACTED], causing the "skill manager" to fail to read the real IP and unable to request the /skills list; hostnames are unaffected by masking. But the hostname is a local value that differs per deployment and must not be copied as-is (this environment currently uses skillmarket.chxia.lab, where chxia.lab is this company's AD domain; other deployments must replace it with their own).
  • Auto (recommended, via Agent deployment): the Agent asks you "Skill market hostname (domain)" during "Chapter 0 · Step 1 collect parameters", then automatically replaces all <market-hostname> in mcp-gateway/skills/skill-market/config.json and the sibling SKILL.md with your value.
  • Manual: edit mcp-gateway/skills/skill-market/config.json (and the SKILL.md fallback address), replace <market-hostname> with your hostname; then make the hostname resolvable — single machine: add a line <server-IP> <your-hostname> in C:\Windows\System32\drivers\etc\hosts (for local debugging you can use 127.0.0.1); company intranet: add an A record in DNS.

Hostname naming suggestion: use an FQDN of "service name + company domain", e.g. skillmarket.your-company-domain (in this environment, skillmarket.chxia.lab). Adding an A record in DNS: DC "Server Manager → DNS → Forward Lookup Zones → your domain → New Host (A) → name skillmarket, IP <server-IP>"; or PowerShell: Add-DnsServerResourceRecordA -Name "skillmarket" -ZoneName "your-domain" -IPv4Address "<server-IP>".

8.9 RAG — unified knowledge-base retrieval (search_knowledge built-in tool)

Note: the MCP Gateway has a built-in search_knowledge tool that forwards to Dify's Knowledge API (Service API, POST /v1/datasets/{id}/hit-testing) for knowledge-base retrieval. DeepChat calls this single tool over MCP to use Dify's unified knowledge base (RAG) — no need for DeepChat to talk to Dify directly.

Overall flow

DeepChat ──MCP──> MCP Gateway (:3100/mcp) ──HTTP──> Dify Knowledge API
                                                      POST /v1/datasets/{id}/hit-testing

Step 1: Dify-side prep (embedding model + knowledge base + Knowledge Key)

  1. Configure an embedding model: Dify admin → Settings → Model Providers → OpenAI-API-compatible → add an embedding model (if the intranet has none, you can run bge-m3 on the host's local Ollama — a 1024-dim Chinese embedding model), then set it as the default text-embedding model in Model Providers (without a default you'll get "Default model not found for text-embedding").
  2. Create a knowledge base: Knowledge → Create → choose High quality indexing → upload documents → configure retrieval params as needed (hybrid search, top_k, score_threshold).
  3. Create a Knowledge API Key: Knowledge → API Access → create a "Knowledge API Key", note:
    • key: a Bearer token with the dataset-... prefix
    • dataset_id: the UUID between /datasets/ and /documents in the knowledge-base URL

Step 2: Configure environment variables

Fill in .env (keep the key in .env, don't hardcode it into gateway.js; sanitize before publishing the repo):

# --- Dify Knowledge API (for the MCP Gateway search_knowledge tool) ---
DIFY_API_BASE=http://<server-IP>/v1
DIFY_KNOWLEDGE_API_KEY=dataset-xxxxx
DIFY_DEFAULT_DATASET_ID=<knowledge-base UUID>

DIFY_API_BASE is injected into the mcp-gateway container (in compose, DIFY_API_BASE=${DIFY_API_BASE}), and also into admin-portal (for the RAG retrieval card on the AI Admin Center's "Dify" page).

Step 3: Restart and verify

  1. docker compose up -d mcp-gateway (or docker restart mcp-gateway)
  2. DeepChat Settings → MCP → connect http://<server-IP>:3100/mcp, call search_knowledge with a query (optional dataset_id, top_k) in a conversation; it returns the most relevant text chunks (each with content + score).
  3. AI Admin Center → "Dify" page → the "🔍 RAG knowledge retrieval" card: type a query to search and display chunks (backend POST /api/dify/retrieve, see 11.5).
⚠️ Key pitfalls:
  • Network reachability: the MCP Gateway is on the ai-platform network while Dify is on its own docker_default network (compose project docker); they can't reach each other by default. Use the host's intranet IP http://<server-IP>/v1 to reach Dify's port 80 from inside the container.
  • Knowledge Key is account-level: one key can access all knowledge bases of that account; Dify's Knowledge API does not directly support "per-user knowledge bases" — you'd need a "user → dataset_id" mapping at the MCP tool layer.
  • GET /v1 returns 308: the retrieval request must use the full path /v1/datasets/{id}/hit-testing, not just /v1.
  • Chinese query via curl -d returns 400 (encoding issue): use --data-binary @file or a script (Python/Node) to send the UTF-8 request.

Alternative access: DeepChat's built-in difyKnowledge (bypassing the MCP Gateway)

The DeepChat client ships a built-in difyKnowledge (in-memory) MCP server that talks to the Dify knowledge base directly, without going through this platform's MCP Gateway. It suits individuals or a very small number of users; for enterprise rollout, still prefer the gateway's search_knowledge (no key leaves the server, auditable, single point to switch datasets).

  1. DeepChat → Settings → MCP settings → find the built-in difyKnowledge → click its edit button → add Dify config.
  2. Fill in three fields (using the values from step 1):
    • API server address (endpoint): http://<server-IP>/v1 (must include /v1)
    • API key (apiKey): the dataset-...-prefixed Knowledge API Key
    • Dataset ID (datasetId): the knowledge base UUID
  3. Back in the chat view, turn on the Dify knowledge base MCP toggle.
⚠️ Notes:
  • The model must support tool/function calling, otherwise retrieval won't be triggered.
  • Key distribution risk: difyKnowledge stores the Knowledge API Key locally on every client; the key is account-level, so spreading it to clients forfeits central control. For enterprise rollout use the gateway's search_knowledge (the key stays only in the server's .env).

13.1 PII masking & content safety (LiteLLM Guardrails)

All requests to external large models go through LiteLLM guardrails preprocessing; sensitive information is masked before leaving the intranet.

1Built-in content filter (enabled by default, no external service)

Uses litellm_content_filter, regex-masking the following types (action = MASK, replace with [xxx_REDACTED] on match):

RuleRegexType
China mobile number\b1[3-9]\d{9}\bcn_mobile
ID card number\b\d{17}[\dXx]\bcn_id
Bank card number\b\d{16,19}\bbank_card
Emailprebuilt emailemail
Unified social credit code\b[0-9A-HJ-NPQRTUWXY]{18}\bcn_credit_code
Passport number\b[EG]\d{8}\bcn_passport
IPv4 address\b\d{1,3}(\.\d{1,3}){3}\bip_address

There's also a sensitive-word blacklist (match → BLOCK reject the request): internal confidential, commercial secret, etc. Add/remove per the company's actual sensitive words in blocked_words in litellm-config.yaml.

⚠️ Key pitfall: after registering guardrails, they're not globally active by default; you must add default_on: true, otherwise they only trigger when the request body explicitly passes a guardrails field.
2Presidio advanced entity recognition (enabled)

Microsoft Presidio (presidio-analyzer / presidio-anonymizer) recognizes finer-grained entities like English names, emails, complementing the built-in regex above. Endpoints set by env vars PRESIDIO_ANALYZER_API_BASE / PRESIDIO_ANONYMIZER_API_BASE.

⚠️ Key pitfall (endpoint format): LiteLLM auto-appends /analyze, /anonymize to the base URL, so the env var must be the base URL (e.g. http://presidio-analyzer:3000), not with the /analyze path, otherwise it becomes /analyze/analyze returning 404. Also the analyzer's /analyze must include the language field (LiteLLM adds it automatically).
⚠️ Slow image pull: presidio-analyzer is ~965MB; direct MCR in China is very slow (~1 hour measured). If it won't pull, use the built-in regex first (already covers core Chinese PII); Presidio is an optional enhancement.
Verify: send a request containing a phone number/email → the original value is replaced with [REDACTED] in the model reply; send one containing "internal confidential" → directly returns Content blocked.

13.10 MailHog mail sink + Ghost passwordless login

Ghost 5 admin is passwordless (no password field in the frontend): entering the email makes Ghost send an email with a 6-digit code. Without SMTP on the intranet this email can't be sent, and login returns Failed to send email. The solution is to add a local mail sink MailHog as the "mail exit", and let the AI Admin Center complete the login automatically.

Admin creation (automated): passwordless login requires Ghost to already have an admin. Run scripts\ghost-setup.ps1 to create the admin in one shot via the setup API (POST /ghost/api/admin/authentication/setup) (email GHOST_ADMIN_EMAIL, password ADMIN_PASSWORD, read from .env), equivalent to the browser wizard, auto-skips if initialized.

ComponentPortPurpose
MailHog8025 (Web UI, SMTP 1025 internal only)Receives Ghost's verification/notification emails, viewable in the browser

Ghost-side env vars (docker-compose.yml):

# Ghost mail → local MailHog (SMTP 1025, no auth)
mail__transport: SMTP
mail__from: noreply@company.com

Ghost passwordless login (AI Admin Center auto-login, no need to check MailHog): Ghost's 6-digit code is essentially TOTP — TOTP(admin_session_secret + userId), 6 digits / 60 s / HMAC-SHA1. So the AI Admin Center can compute the code locally, without digging through MailHog emails. Clicking "Open" on the "Ghost Admin" entry, the backend POST /api/ghost/auto-login does in order:

  1. Password login POST /ghost/api/admin/session/ (email + password) → get an unverified session cookie (this triggers the code email, swallowed by MailHog, which we ignore);
  2. Read Ghost DB's settings table admin_session_secret + admin userId, compute the TOTP code locally;
  3. PUT /ghost/api/admin/session/verify (with cookie + computed code) → session verified;
  4. Write the ghost-admin-api-session cookie into the browser (Path=/ghost, cookies shared by domain across ports on the same host), redirect to :8090/ghost/ straight into the admin.
⚠️ Key pitfalls: ① Ghost 5's backend still supports password login (POST /session/), but a correct password triggers "new device 2FA" (returns 403 Needs2FAError + sends a code), so the verification step is required; ② the code is TOTP, reproducible exactly with crypto.createHmac('sha1', secret+userId), verified to match the emailed code digit-for-digit; ③ even computing the code yourself, Ghost still really "sends email", so MailHog (or any SMTP) must be kept, otherwise login returns Failed to send email; ④ /session/verify has brute-force rate limiting; a normal single click won't trigger it, but don't spam it repeatedly in a short time.
