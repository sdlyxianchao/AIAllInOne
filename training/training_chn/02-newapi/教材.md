# NewAPI 教材（M04 · LLM 路由网关）

> 平台内 NewAPI 端口 `3000`（容器 `new-api`），数据库 MySQL（`new-api-db`），Redis 缓存（`new-api-redis`）。

## 1. NewAPI 是什么

NewAPI 是基于 OneAPI 二次开发的开源 **LLM 网关 / AI 资产管理系统**：把 OpenAI、Claude、Gemini、DeepSeek 等异构模型统一成 **OpenAI 兼容接口**，提供渠道管理、令牌分发、额度计费、限流、日志统计。在本平台中，NewAPI 是**员工使用 AI 的统一入口**：

```
DeepChat / Dify ──> NewAPI(:3000) ──> LiteLLM(:4000，PII 脱敏) ──> 外部大模型
```

## 2. 平台内关键约定

| 约定 | 值 |
|---|---|
| 访问地址 | `http://<服务器IP>:3000`（员工）/ `http://127.0.0.1:3000`（本机） |
| 管理员账号 | 统一 `ai_all_in_one_admin`（首装向导创建本地管理员） |
| 使用模式 | **个人使用**（内部使用；对外运营含充值计费，演示站点只读） |
| 渠道 Base URL | `http://litellm:4000`（容器名，走 Docker 网络） |
| 渠道密钥 | `.env` 中 `LITELLM_MASTER_KEY` |
| 关键环境变量 | `DEFAULT_QUOTA=100`（新用户送 100 美元额度）、`GENERATE_DEFAULT_TOKEN=true`（自动生成初始 token）、限流 4 变量 |

## 3. 首次初始化向导（四步）

1. **数据库检查** → 点击"验证数据库连接"（MySQL 通即绿勾）。
2. **管理员账户** → 用户名 `ai_all_in_one_admin`、邮箱 `ai_all_in_one_admin@<公司域名>`、统一密码（≥8 位）。
   > 此时 OIDC 未配，必须创建本地管理员先"进门"。
3. **使用模式** → 选 **个人使用**。
4. **审核并初始化** → 确认后自动建表 → 登录。

## 4. 渠道与密钥

### 4.1 添加 LLM 渠道（指向 LiteLLM）
- **渠道** → 添加新的渠道：
  - 类型：`OpenAI`；名称：`LiteLLM-OpenAI`
  - Base URL：`http://litellm:4000`（⚠️ 容器名，不是 localhost）
  - 密钥：`.env` 中 `LITELLM_MASTER_KEY` 的实际值
  - 模型：`gpt-4o, gpt-4o-mini`（或你实际启用的模型，如 `deepseek-chat`）
- Claude 渠道：类型 `Anthropic Claude`，Base URL 同样 `http://litellm:4000`。
- DeepSeek 渠道：类型 `OpenAI`，模型 `deepseek-chat`。
- 保存后点渠道 **测试** → 有回复即链路通（NewAPI → LiteLLM → 外部模型）。

### 4.2 创建 API 密钥
- **API 密钥** → 新建：
  - `dify-key`：给 Dify 服务端调用（服务端密钥）。
  - `deepchat-key`：给 DeepChat 客户端调用。
- **为什么分开**：用量可分别统计，出问题易定位。

### 4.3 员工自助申请
- 新用户注册/首次 OIDC 登录时，若 `.env` 设了 `DEFAULT_QUOTA=100` + `GENERATE_DEFAULT_TOKEN=true`，自动获得 100 美元额度与初始 token。
- ⚠️ 只对**新注册**用户生效；老用户需管理员在「用户 → 编辑 → 手动设置额度」。

## 5. Keycloak OIDC 接入（重点）

### 5.1 Keycloak 侧（已在 M03 完成）
Client ID `newapi`，Client authentication On，redirect URIs 含内网与本机两个地址。

### 5.2 NewAPI 侧
1. **系统设置 → 身份验证 → 自定义 OAuth → 添加 OAuth 提供商**：
   - 预设模板：`Keycloak`；API 地址：`http://127.0.0.1:9090`（快速设置自动带出）
   - 提供商名称 `Keycloak`、Client ID `newapi`、Client Secret（从 Keycloak 复制）
   - Well-Known URL：`http://host.docker.internal:9090/realms/enterprise-ai/.well-known/openid-configuration` → 点 **自动发现**
   - ⚠️ **手动修正**：授权端点保持 `<服务器IP>:9090`（浏览器跳转用）；**令牌端点、用户信息端点改为 `host.docker.internal:9090`**（NewAPI 容器内部访问宿主机）
   - 作用域 `openid profile email`；字段映射 `sub` / `preferred_username` / `name` / `email`
2. **⚠️ 服务器地址必须设为内网地址**：系统设置 → 通用设置 → 服务器地址 `http://<服务器IP>:3000`。
   > 原因：换 token 时用服务器地址拼 redirect_uri，与浏览器访问地址不一致会报 `invalid_grant`。设成内网 IP 后，本机也要用内网 IP 访问（别点 127.0.0.1）。
3. **SSO 管理员提权**：OIDC 登录用户默认 common 角色（role=1），访问管理页 403。修复：
   ```
   docker exec new-api-db mysql -uroot -p... new-api -e "SELECT user_id, provider_user_id FROM user_oauth_bindings;"
   docker exec new-api-db mysql -uroot -p... new-api -e "UPDATE users SET role=100 WHERE id=<user_id>;"
   docker restart new-api
   ```
4. 登录页出现 **Keycloak 按钮** → 用 AD 账号测试登录。

## 6. 用量、成本与审计

| 功能 | 位置 | 说明 |
|---|---|---|
| 仪表盘 | 首页 | 请求数、token 消耗、渠道负载 |
| 使用日志 | 日志页 | 每次调用明细（用户/模型/token/额度/IP/时间） |
| 成本报表 | AI 管理中心 → NewAPI 管理 | 按用户/模型/日期聚合（1 美元 = 500000 额度） |
| 审计日志 | AI 管理中心 → NewAPI 管理 | 最近 100 条调用记录，用于合规追溯 |
| 分组配额 | 分组管理 | 按部门分组，设置模型倍率/额度；链路：AD 组 → Keycloak 角色 → NewAPI 分组 → 模型权限 |

## 7. 限流参数（.env，防 OIDC 调试 429）

| 变量 | 说明 |
|---|---|
| `GLOBAL_WEB_RATE_LIMIT` | Web 登录限流（次/分钟），测试期 999999 |
| `GLOBAL_API_RATE_LIMIT` | API 路由限流（次/3 分钟），测试期 999999 |
| `CRITICAL_RATE_LIMIT_ENABLE` | 关键接口限流开关（登录/OAuth 回调），测试期 false |
| `CRITICAL_RATE_LIMIT` | 关键接口阈值，测试期 999999 |

临时清限流：`docker exec new-api-redis redis-cli --scan --pattern "rateLimit:*" | xargs -r docker exec new-api-redis redis-cli DEL`

## 8. 常见问题

| 症状 | 根因与解决 |
|---|---|
| 渠道测试失败 | LiteLLM 密钥错（用 .env 实际值）、外部模型 Key 未配、看 `docker logs litellm` |
| 报 `No connected db` | 渠道密钥不是 LITELLM_MASTER_KEY 实际值 |
| OIDC 换 token 报 invalid_grant | 服务器地址未设内网 IP / redirect_uri 不一致 |
| SSO 登录 403 | role 未提权（见 5.2-3） |
| 登录 429 | 限流触发，清 Redis 或调 .env 后重建容器 |
| 员工额度为 0 | 老用户不享受 DEFAULT_QUOTA，需手动调整额度 |

## 9. 安全要点
- 上游真实 Key 只放 NewAPI 后台渠道，员工只拿令牌（token）。
- 令牌按用途分开、设置额度与有效期；离职及时停用。
- 服务器地址/端口只在内网开放，生产建议 HTTPS。
