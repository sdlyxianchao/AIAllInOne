# AI AllInOne — منصة الذكاء الاصطناعي للشبكة الداخلية للمؤسسات (متعددة المنصات، مستضافة ذاتياً)

> 📖 **اللغات**: [English](../README.md) · [简体中文](README.zh.md) · [繁體中文](README.zh-TW.md) · [Français](README.fr.md) · [Español](README.es.md) · [Português](README.pt.md) · [日本語](README.ja.md) · [한국어](README.ko.md) · [العربية](README.ar.md)

حزمة ذكاء اصطناعي **جاهزة للاستخدام ومتعددة المنصات** للشبكة الداخلية للمؤسسات: توحيد المصادقة، وتوجيه النماذج اللغوية (LLM)، وإخفاء البيانات الشخصية (PII)، وتطبيقات الذكاء الاصطناعي، وبوابة المؤسسة، والمصدر/التكامل المستمر، وتوزيع العميل، والإدارة الموحدة، والمراقبة والتنبيهات، والملاحظة، والتسجيل، والنسخ الاحتياطي/الاستعادة — كل ذلك منسّق عبر Docker في نظام واحد متكامل، مع **دخول موحّد (SSO) لجميع المنتجات عبر حساب Keycloak واحد**.

يدعم المستودع ثلاث منصات نشر:

| المنصة | مجلد المستودع (على GitHub) | حالة الاستخدام النموذجية |
|---|---|---|
| Windows | `windows/` | Windows 11 + Docker Desktop (جهاز واحد) |
| Linux / macOS | `linux/` | خادم Linux مستضاف ذاتياً / macOS (Docker) |
| خادم عبر الإنترنت | `docker/` | سحابة / مضيف Docker خام (إنتاج) |

> في مجلد العمل المحلي، تُسمّى هذه المجلدات `windows-github/` و`linux-github/` و`docker-github/`؛ وبعد الرفع إلى GitHub تُحذف اللاحقة `-github` لتصبح `windows/` و`linux/` و`docker/`. كل تحديث مستقبلي يتبع هذا التعيين نفسه.

## 1. ما الذي يتضمنه

| الطبقة | المكوّن | الغرض |
|---|---|---|
| المصادقة | Keycloak | SSO / OIDC، يمكن التكامل مع AD/LDAP أو الحسابات المحلية |
| توجيه LLM | NewAPI | القنوات، المفاتيح، الحصص، التدقيق، التكلفة |
| إخفاء PII | LiteLLM + Presidio | إخفاء تلقائي لأرقام الهواتف/الهويات/البريد قبل استدعاء النموذج |
| تطبيقات الذكاء الاصطناعي | Dify | منصة تطبيقات ذكاء اصطناعي مرئية / وكلاء |
| بوابة المؤسسة | Ghost | إعلانات الشركة وبوابة الأخبار |
| المصدر / CI | Gitea + Runner | Git داخلي + أتمتة Actions |
| العميل | DeepChat | عميل ذكاء اصطناعي محلي لسطح المكتب (Windows / macOS / Linux) |
| توزيع العميل | Update Server | استضافة مُثبّت DeepChat وتحديثه تلقائياً |
| الإدارة الموحدة | AI Admin Center | نقطة دخول واحدة: لوحة تحكم + منتجات مضمّنة + تدقيق/تكلفة/تقارير |
| البوابة | MCP Gateway | إدارة سوق المهارات / MCP |
| المراقبة | Prometheus + Grafana + Alertmanager | مراقبة موارد الحاويات + إشعارات التنبيه |
| ملاحظة LLM | Langfuse | تتبّع / زمن الاستجابة / الرموز / تكلفة كل استدعاء نموذج |
| التسجيل الموحّد | Loki + Promtail | سجلات مجمّعة وقابلة للبحث من جميع الحاويات |
| النسخ الاحتياطي/الاستعادة | سكربتات backup/restore + صفحة إدارة | نسخ احتياطي كامل يومي + استعادة بنقرة واحدة |

يحتوي كل مجلد منصة على: `docker-compose.yml`، و`.env.example`، و`*-deploy-guide*.html` (دليل النشر)، و`*-checklist*.html` (قائمة تحقق التقدم)، ودليل تكامل مزوّد الهوية، وسكربتات نشر بنقرة واحدة، بالإضافة إلى كود المصدر والإعدادات المنقّاة. **لا يُرفع أي سرّ حقيقي.**

### البنية وتدفق البيانات

تُنظَّم المكوّنات في طبقات، وكلها مُنسَّقة بواسطة Docker على شبكة واحدة `ai-platform` (تتواصل الحاويات فيما بينها بأسماء الحاويات، وليس عبر `localhost`):

- **طبقة المستخدم** — عميل سطح المكتب DeepChat + مستخدمو المتصفح.
- **البوابة والتطبيقات** — بوابة Ghost المؤسسية (`:8090`) ومنصة تطبيقات الذكاء الاصطناعي Dify على الويب (`:80`).
- **توجيه LLM** — NewAPI (`:3000`، توجيه / فوترة / تحديد المعدل) → LiteLLM + Presidio (`:4000`، إخفاء بيانات PII) → النماذج الخارجية.
- **قابلية الملاحظة** — Langfuse (`:3010`) يتتبع كل استدعاء نموذج.
- **البنية التحتية** — Keycloak (`:9090`، SSO / OIDC / RBAC)، وMCP Gateway، وGitea (`:3002`)، وخادم التحديثات (`:8091`)، والمراقبة/السجلات (Prometheus / Grafana / cadvisor / Loki).
- **الإدارة الموحّدة** — **موقع AI Admin Center** (`:10086`): بوابة الإدارة الوحيدة، المعتمدة عبر Keycloak، وتوفّر مدخلاً واحداً إلى لوحة التحكم، وصفحة إدارة كل منتج، وتقارير التدقيق/التكلفة، والنسخ الاحتياطي/الاستعادة، والسجلات الموحّدة.

تدفقات البيانات الرئيسية:

1. **طلب LLM (السلسلة الأساسية)** — DeepChat / Dify → NewAPI (`:3000`) → LiteLLM يُخفي PII (`:4000`) → النموذج الخارجي → LiteLLM يستعيد PII → إعادة الاستجابة؛ ويبلّغ `success_callback` في LiteLLM عن كل استدعاء إلى Langfuse.
2. **وصول المستخدم** — المتصفح → بوابة Ghost (`:8090`) → الأخبار / التنزيلات → الانتقال إلى Dify (`:80`)؛ ويفتح المدراء AI Admin Center (`:10086`).
3. **المصادقة (SSO)** — يوفر Keycloak OIDC تسجيل دخول واحداً لجميع منتجات الويب (حساب مدير مشترك `ai_all_in_one_admin`).
4. **التحديث التلقائي** — Gitea Actions يبني → خادم التحديثات (`:8091`) يستضيف المثبّتات → DeepChat يتنزّل تلقائياً عبر `version.txt`.
5. **Skill / MCP** — يقدّم MCP Gateway أدوات Skill/MCP إلى DeepChat وDify.
6. **المراقبة والسجلات الموحّدة** — Prometheus / cadvisor → Grafana (`:3030`)؛ يجمع Promtail سجلات الحاويات → Loki (`:3110`) → تُعرض في صفحة «السجلات الموحّدة» في AI Admin Center.

## 2. البدء السريع: النشر الآلي عبر أداة من نوع Harness (موصى به)

يمكن للأدوات من نوع Harness (OpenClaw وMicrosoft Scout وWorkBuddy وما شابهها) قراءة وثائق هذا المشروع وإعداداته وبناء البيئة كاملة خطوة بخطوة على جهازك. فيما يلي المسار القياسي.

### 5 متطلبات مسبقة

**1. تثبيت أداة من نوع Harness**
ثبّت OpenClaw أو Microsoft Scout أو WorkBuddy (أو ما يعادلها). جميعها تستطيع قراءة/كتابة الملفات المحلية، وتنفيذ الأوامر، والبحث في الويب.

**2. شراء اشتراك أو إعداد واجهة برمجة التطبيقات الخاصة بك**
أكمل الاشتراك في الأداة، أو أدخل مفتاح واجهة برمجة التطبيقات الخاص بنموذجك اللغوي (DeepSeek / OpenAI / Claude / Qwen / ERNIE وغيرها) حتى تتمكن الأداة من المحادثة بشكل طبيعي.

**3. تجهيز بيئة الشبكة**
هذه هي الخطوة التي تعطّل معظم المستخدمين:
- تأكد من قدرة الجهاز على الوصول إلى **سجلات صور Docker** (Docker Hub / quay.io وغيرها). إذا تعذّر الوصول المباشر، فعليك إعداد مرآة سجلّ (مثل DaoCloud) مسبقاً.
- تأكد من الوصول إلى **GitHub** (لاستنساخ المستودع وسحب بعض الاعتماديات العامة). إذا تعذّر الوصول المباشر، استخدم وكيلاً أو نزّل حزمة المصدر مسبقاً.
- تأكد من إمكانية الوصول إلى الجهاز المستهدف على مقطع الشبكة الذي تنوي كشفه.

**4. استنساخ المستودع أو تنزيل المشروع محلياً**
```bash
git clone <عنوان-مستودعك> AIAllInOne
# أو نزّل الأرشيف وفكّ ضغطه في أي مجلد محلي
```

**5. الصق الموجه أدناه في الأداة لبدء النشر الآلي**

انسخ **الموجه بالكامل** أدناه إلى مربع إدخال أداة Harness، ثم أجب عن أسئلتها واحداً تلو الآخر. ستقوم الأداة بما يلي: اكتشاف منصتك → جمع المعاملات → إنشاء ملف تقدم محلي → الإعداد خطوة بخطوة وفق الدليل → التكرار معك لاختبار المشكلات وإصلاحها → إبقاء التقدم محدّثاً → تنفيذ اختبار كامل في النهاية وإبلاغك بالنتائج.

### موجه النشر بنقرة واحدة (انسخه إلى الأداة)

````text
أنت مهندس نشر لمنصة ذكاء اصطناعي للشبكة الداخلية للمؤسسات. بناءً على وثائق هذا المشروع وملفات إعداداته، انشر منصة "AI AllInOne" بالكامل على الجهاز الحالي وتحقق منها. تواصل معي باللغة العربية طوال الوقت واتبع الإجراء أدناه بدقة.

## الخطوة 1: تأكيد مجلد النشر والمنصة المستهدفة

1. اسألني أولاً: ما هو المسار المحلي لاستخراج/استنساخ هذا المشروع؟ (مثال: C:\AIAllInOne أو /opt/AIAllInOne)
2. بعد الدخول إلى ذلك المجلد، حدّد مجلد المنصة المستهدفة وفق نظام تشغيل الجهاز:
   - Windows → استخدم مجلد `windows-github` (أو `windows`)
   - Linux / macOS → استخدم مجلد `linux-github` (أو `linux`)
   - خادم عبر الإنترنت / بيئة Docker خالصة → استخدم مجلد `docker-github` (أو `docker`)
   إذا لم تكن متأكداً، أخبرني بنظام التشغيل الذي اكتشفته وتأكد معي من المجلد المطلوب استخدامه.
3. اقرأ README.md الجذري وREADME.md داخل مجلد المنصة لفهم البنية ونهج النشر قبل التصرف.

## الخطوة 2: جمع المعاملات المطلوبة (اسألني واحداً تلو الآخر؛ لا تتخطَّ ولا تخمّن)

قبل الإعداد، اجمع المعلومات التالية، واسألني عن أي عنصر ناقص واشرح الغرض من كل عنصر:

1. عنوان IP للشبكة الداخلية المستخدم لكشف المنصة (العنوان الذي تستخدمه الأجهزة الأخرى للوصول إليها، مثال: 192.168.1.100).
2. مصدر الهوية (Identity Provider):
   - وحدة تحكم نطاق AD الخاصة بالشركة (Active Directory): اسألني عن اسم النطاق، وعنوان IP لوحدة التحكم، وbase DN الخاص بـLDAP، وbind DN، وكلمة مرور حساب الربط، وsAMAccountName، وغيرها.
   - مزوّد هوية آخر (LDAP/OpenLDAP/OIDC/Feishu/WeCom/DingTalk وغيرها): اسألني عن الإعدادات ومعلومات الحساب المقابلة.
   - لا مصدر هوية خارجي (حسابات محلية فقط): تأكد معي ثم تخطَّ.
3. حساب المسؤول الموحّد: اسم المستخدم، كلمة المرور، البريد الإلكتروني (لدخول Keycloak SSO ودخول المسؤول لكل منتج).
4. مفاتيح API للنماذج اللغوية: أي مزوّدي نماذج وأي مفاتيح أملكها فعلياً (DeepSeek / OpenAI / Claude / Qwen / ERNIE وغيرها)؛ تخطَّ ما لا أملكه.
5. عناصر أخرى تُسأل حسب الحاجة: قناة إشعار التنبيه (عنوان webhook لـDingTalk/WeCom/Feishu)، شهادات HTTPS، سياسة الاحتفاظ بالنسخ الاحتياطية، وغيرها.

## الخطوة 3: إنشاء ملف تقدم محلي

1. حدّد مستند "قائمة التحقق" في مجلد المنصة (مثال: *-checklist*.html) و"دليل تكامل مصدر الهوية" (مثال: *-ad-integration*.html أو مستندات متعلقة بمزوّد الهوية).
2. بناءً على محتوى القائمة، أنشئ ملف تقدم جديداً في مجلد المشروع، باسم مثل "deployment-progress-<المنصة>-<التاريخ>.md"، مع نسخ كل عنصر من القائمة كغير مكتمل (- [ ]).
3. من الآن فصاعداً، حدّث هذا الملف فوراً في كل مرة تكمل فيها عنصراً أو تحل مشكلة، وأبلغني بالتقدم بإيجاز في المحادثة.

## الخطوة 4: الإعداد خطوة بخطوة وفق دليل النشر

1. اقرأ بعناية "دليل النشر" الخاص بالمنصة (مثال: *-deploy-guide*.html) واتّبعه بدقة، مع إيلاء اهتمام خاص لما يحدده من "⚠️ مطبات حرجة / نقاط تعثر".
2. الترتيب التقريبي: تجهيز متغيرات البيئة → تشغيل الحاويات → تهيئة المصادقة/مزوّد الهوية → إعداد توجيه LLM وقنوات النماذج → تهيئة كل منتج → إعداد المراقبة/الملاحظة/التسجيل/الإخفاء → إعداد النسخ الاحتياطي والاستعادة.
3. فضّل سكربتات الأتمتة الموجودة في المجلد (مثل bootstrap.ps1 وkeycloak-realm-init.ps1 وhealth-check وغيرها)؛ لا تنقر في الواجهات للخطوات القابلة للأتمتة.

## الخطوة 5: التكرار معي لاختبار المشكلات وإصلاحها

1. عند فشل خطوة أو عدم مطابقتها للتوقعات، افحص السجلات أولاً (docker logs، ونقاط نهاية الصحة لكل خدمة، وملفات الإعداد)، وحدّد السبب الجذري ثم أصلحه — لا تعِد المحاولة بشكل أعمى.
2. عندما تحتاج مشاركتي (مثل تنفيذ أمر بصلاحيات مسؤول، تأكيد تسجيل دخول، تقديم معلومات إضافية)، أخبرني بوضوح "ماذا تفعل ولماذا".
3. بعد الحل، سجّل السبب الجذري والإصلاح في ملف التقدم وأبلغني بإيجاز.

## الخطوة 6: التحقق الكامل من البداية إلى النهاية

بمجرد اكتمال كل عناصر القائمة، نفّذ اختباراً كاملاً من البداية إلى النهاية يغطي على الأقل:
- صحة الخدمات (جميع الحاويات تعمل، ونقاط نهاية الصحة طبيعية)؛
- الدخول الموحّد SSO (دخول Keycloak → دخول موحّد/تلقائي لكل منتج)؛
- سلسلة LLM (أرسل محادثة حقيقية واحدة عبر NewAPI/LiteLLM، وتحقق من الاستجابة + عمل إخفاء PII)؛
- الدخول عبر مصدر الهوية (إذا كان AD/مزوّد هوية آخر متصلاً، اختبر الدخول بالحساب المقابل)؛
- المراقبة/الملاحظة/التسجيل/التنبيهات (تأكد من وجود البيانات وإمكانية إطلاق التنبيهات)؛
- النسخ الاحتياطي والاستعادة (نفّذ نسخة احتياطية وتحقق من إمكانية استعادتها).

أخيراً، لخّص نتائج الاختبار عنصراً بعنصر، مع تمييز واضح بـ ✅ ناجح / ❌ فاشل؛ وبالنسبة للفاشل، اذكر السبب الجذري واقتراحات المتابعة.
````

## 3. النشر اليدوي (بديل)

إذا كنت تفضّل عدم استخدام أداة من نوع Harness، يمكنك النشر يدوياً باتباع `README.md` و`*-deploy-guide*.html` لكل منصة. المسار الرئيسي هو نفسه: تشغيل الحاويات → تهيئة المصادقة/مزوّد الهوية → إعداد قنوات LLM → تهيئة كل منتج → إعداد المراقبة/النسخ الاحتياطي.

## 4. الأمان والملاحظات

- لا يحتوي هذا المستودع على **أي سرّ حقيقي**؛ جميع القيم الحقيقية موجودة في ملف `.env` لكل بيئة تشغيل (تُرفع فقط قوالب `.env.example`).
- الإعداد الافتراضي هو HTTP نصي واضح على الشبكة الداخلية؛ للتعرف على HTTPS راجع الفصل ذي الصلة في دليل النشر لكل منصة.
- توجد المطبات ومخططات البنية وجداول المنافذ وتدفقات البيانات لكل منصة في مستندات `*-deploy-guide*.html` المقابلة.
