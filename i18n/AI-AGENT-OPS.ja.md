# AI エージェント運用ガイド

> 📖 **言語**: [English](../AI-AGENT-OPS.md) · [简体中文](AI-AGENT-OPS.zh.md) · [繁體中文](AI-AGENT-OPS.zh-TW.md) · [Français](AI-AGENT-OPS.fr.md) · [Español](AI-AGENT-OPS.es.md) · [Português](AI-AGENT-OPS.pt.md) · [日本語](AI-AGENT-OPS.ja.md) · [한국어](AI-AGENT-OPS.ko.md) · [العربية](AI-AGENT-OPS.ar.md)

このプラットフォームは「**AI エージェントによる運用・保守**」を前提に設計されています。WorkBuddy、OpenClaw、Microsoft Scout、あるいは同等のツールであればどれでも使えます。十数個の管理コンソールにログインして UI をクリックして回る代わりに、自然言語でエージェントにやりたいことを伝えるだけで、エージェントがファイルを読み、コマンドを実行し、各サービスとやり取りしてくれます。

このガイドでは、AI エージェントを使った日常運用の方法を説明します：ヘルスチェック、コンテナ管理、設定変更、AI 管理センター、Gitea／同期、Ghost ポータル、バックアップ、リリース、トラブルシューティング。

---

## 1. 仕組み

プラットフォームを動かすすべてのものは、あなたのローカルマシン上に**コード・設定・データ**として存在します：

- **Docker Compose** がすべてのコンテナを定義します。
- **`.env` ファイル**（例：`windows/.env.windows`）がサービスで使う資格情報を保持します。
- **管理 API** が管理エンドポイントを公開します（Keycloak、Gitea、NewAPI など）。
- **ファイルとデータベース**（Ghost の SQLite DB、DSH Desktop のインストーラー、同期履歴 JSON など）が実際の状態です。

エージェントにできること：

- **任意のファイルの読み書き**——設定、スクリプト、AI 管理センターの `index.html` / `server.js`、ドキュメント。
- **コマンドの実行**——`docker`、`docker compose`、`git`、PowerShell、Node.js、Python。
- **HTTP でのサービス呼び出し**——管理 API、ヘルスエンドポイント、ダウンロードリンク。
- **必要に応じた Web 検索**で製品ドキュメントを調べる。

すべてが「ファイル + コマンド + API」で成り立っているため、エージェントはそのすべてを見て変更できます。だからこそ、プラットフォーム全体をエージェント経由で運用できるのです。

---

## 2. 準備（一度だけ）

1. **エージェントでプロジェクトフォルダーを開く。** エージェントの作業ディレクトリをプロジェクトルート（例：`C:\AIAllInOne`）に向けます。ここで `docker-compose.yml`、`.env` ファイル、スクリプト、ドキュメントを読みます。
2. **Docker Desktop が起動していることを確認する。** ほとんどの操作は `docker` / `docker compose` コマンドです。Docker Desktop が停止している場合、エージェントの最初のステップは通常、確認して起動することです。
3. **資格情報は `.env` に置き、チャットには置かない。** エージェントはサービスパスワードを `windows/.env.windows` から読みます。実パスワードを会話やコミット済みファイルに貼り付けないでください。
4. **使うプラットフォームフォルダーを伝える**（不明な場合。単一マシンでは通常 `windows/`）。

## 3. エージェントができること

| タスク | エージェントの方法 |
|---|---|
| ヘルスチェック／状態の概要 | `docker ps` + ヘルスエンドポイント + 管理 API |
| サービスの起動／再起動／停止 | `docker compose up -d <svc>` / `docker restart <svc>` |
| ログとエラーの確認 | `docker logs <svc> --tail N`、ログファイルの読み取り |
| 設定変更 | ファイルを編集し、影響するコンテナを再起動 |
| AI 管理センターの編集 | `admin-portal/public/index.html`（UI）または `admin-portal/server.js`（API）を編集 |
| Gitea + 同期の管理 | Gitea API：ワークフローのトリガー、実行状態／ログの読み取り、リポジトリファイルの編集 |
| Ghost ポータルの管理 | Ghost の SQLite DB の読み書き、テーマテンプレートの編集、サンプルコンテンツのインポート |
| バックアップと復元 | `scripts/backup.ps1` / `scripts/restore.ps1` |
| リリースの公開 | `publish.ps1`（ビルド + コミット + GitHub へのプッシュ） |
| クリーンアップ | `docker image prune`、古いバックアップの削除など（要確認） |
| トラブルシューティング | ポート競合、Docker Desktop の問題、DNS／プロキシなど |

## 4. よくあるタスクと例文

以下は、もっとも頻繁に行うタスクと、それぞれの例文です。自分の言語で話しかけてかまいません。エージェントは理解します。`<…>` は実際の値に置き換えてください。

### 4.1 全体のヘルスチェック

> 「すべてのサービスが稼働していて健全か確認して。停止中または再起動を繰り返しているコンテナを列挙し、理由を教えて。」

エージェントは `docker ps` を実行し、各ヘルスエンドポイントを叩いて状態を報告します。

### 4.2 停止・エラー中のサービスの調査

> 「LiteLLM が停止しています。原因を突き止めて直し、復旧したことを確認して。」

エージェントはコンテナの状態を調べ、ログを読み、根本原因（例：ポート競合）を見つけて修正します。

### 4.3 サービスの再起動

> 「server.js の変更を反映するために admin portal を再起動して。」

エージェントは `docker restart admin-portal` を実行します。注意：**バックエンド**のコード（`server.js`）変更はコンテナの再起動が必要ですが、**フロントエンド**（`index.html`）の変更はブラウザのリロードだけで済みます。

### 4.4 ログの確認

> 「Gitea runner のログの最後の 50 行を見せて、エラーがあるか教えて。」

### 4.5 DSH Desktop 同期の管理（Gitea）

> 「dsh-sync ワークフローをトリガーして、進捗を見せて——フェーズ、ダウンロード済みファイル数、MB、残り時間。」

エージェントは Gitea API を呼んでワークフローをトリガーし、実行状態をポーリングして `sync-progress.json` を読みます。

### 4.6 AI 管理センターの変更

> 「Gitea のリポジトリ一覧にページネーションを追加して——1 ページ 10 件、調整可能で。」

エージェントは `index.html` を編集し、JavaScript を検証し、（バックエンド変更の場合）コンテナを再起動します。その後、ブラウザをハードリロード（Ctrl+F5）します。

### 4.7 Ghost ポータルの管理

> 「サンプルコンテンツをポータルにインポートして。アドレス 192.168.1.100、中国語で。」

エージェントは公開アドレスと言語を尋ね、`ghost-content-import.ps1` を実行します。テーマの修正、ページの編集、ナビゲーションの DB 直接変更も可能です。

### 4.8 バックアップと復元

> 「今すぐ完全バックアップを実行して、成功したか確認して。」

### 4.9 GitHub へのリリース公開

> 「新しいリリース v0.7 を公開して。コミットメッセージは 'feat: …'。」

エージェントは `publish.ps1 -Version v0.7 -CommitMessage "…"` を実行します。注意：`git push` にはプロキシまたは GitHub 資格情報が必要です。ネットワークでプッシュが失敗した場合、エージェントはプロキシを開くよう促します。

### 4.10 ディスク容量のクリーンアップ

> 「Docker のディスク使用量の内訳と、安全に削除できるものを教えて。」

エージェントはスキャンし（`docker system df`、未使用イメージ、ボリューム、古いバックアップ）、候補を列挙します——**削除は、あなたがどれを削除するか確認してからだけ行います。**

## 5. ベストプラクティスと注意点

- **フロントエンド vs バックエンドの反映。** AI 管理センターでは、`index.html` の変更はブラウザのリロードで反映されます（ファイルはボリュームマウント）。`server.js` の変更は `docker restart admin-portal` が必要で、単なる `docker compose up -d` ではボリュームマウントされたコードは**再読み込みされません**。
- **ブラウザのハードリロード**（Ctrl+F5）：UI が変わらないように見えるときは、古い JavaScript がキャッシュされていることが多いです。
- **実シークレットや IP をコミットしない。** プレースホルダー（例：`<服务器IP>`、`CHANGE_ME_*`）を使います。`publish.ps1` は `server.js` のパスワードを自動でサニタイズします。
- **検証する。鵜呑みにしない。** エージェントにはコマンドで結果を示してもらいましょう（HTTP ステータス、`ls`、ログ行）。特に「直りました」という報告のときは。
- **破壊的な変更の前にバックアップ。** エージェントは Ghost DB や設定を編集する前にバックアップし、何かを削除する前に確認を取るべきです。
- **コンテンツインポート前に言語とアドレスを確認。** ポータルコンテンツをインポートする際、エージェントはまず公開アドレスと対象言語を尋ねるべきです。
- **ネットワークとプロキシ。** 一部の手順（GitHub へのプッシュ、Web 検索）はプロキシ（例：`127.0.0.1:33210`）または外向きネットワークが必要です。ネットワーク手順が失敗したら、プロキシを開いて再試行してください。

## 6. コマンド早見表

| 操作 | コマンド |
|---|---|
| コンテナ一覧 | `docker ps -a` |
| コンテナログ | `docker logs <名前> --tail 100` |
| サービスの再起動 | `docker restart <名前>` |
| 全サービスの起動 | `docker compose up -d` |
| Compose の状態 | `docker compose ps` |
| Gitea 同期のトリガー | `POST /api/v1/repos/<user>/dsh-sync/actions/workflows/sync.yml/dispatches` |
| バックアップ実行 | `powershell .\scripts\backup.ps1` |
| リリース公開 | `powershell .\publish.ps1 -Version v0.x -CommitMessage "…"` |
